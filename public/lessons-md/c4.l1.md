# C4.L1 — A Different Machine, Not a Faster Loop

_Track C4: Vectorized Execution · ~16 min · columnspaces_

> A batch of one row costs 1,662,333 modelled operations. Tuple-at-a-time costs 1,351,892 for the same answer. Batching is not a faster loop — it is a machine with a fixed cost per batch, and below eight rows it loses.
Tuple-at-a-time execution is not slow because its loop is badly written. It is expensive because it pays a fixed toll **per row**, and the toll has nothing to do with your data.

Walk one row through a three-operator pipeline — scan, filter, aggregate — and count what happens that is not arithmetic on your values:

- a call across each operator boundary (virtual, because the operator is chosen at plan time, not compile time)
- a has-next branch to find out whether there is another row
- a validity check, because the value might be null
- a branch per comparison, taken on data the branch predictor cannot learn
- and for a surviving row, a materialised tuple to hand upward, because `next()` returns a row and a row has to exist

The `batch-machine` lab in this lesson charges for exactly those and nothing else. On a column of **131,072 rows**, tuple-at-a-time costs **1,361,445 modelled operations — 10.39 per row** — of which **393,216 are virtual calls** (three per row, one per operator boundary) and **350,967 are branches**. The answer itself is two accumulator updates per surviving row. Nearly all of that count is bookkeeping.

This lesson is not about making that loop faster. It is about replacing the machine. **→ tablespace T5.L1 and T7.L2** already derive the volcano iterator model and why a row store's operator interface looks the way it does; this course does not re-derive it. What matters here is what changes when the unit of work stops being a row.

---

## Three things change, and only three

Take the same query — `select count(*), sum(v) where v >= 300 and v <= 700` — and give every operator a **vector** instead of a row.

**1. The per-operator overhead is charged once per batch.** Three virtual calls per *batch* instead of three per row. At a batch of 2,048 that is 64 batches, so 192 virtual calls replace 393,216.

**2. The validity question is asked once per vector.** A batch either contains a null or it does not, and that is one check against a null count, not one check per row. Only when the vector is impure does the operator pay per row. This is the reason a real engine carries a validity bitmap per vector rather than an `Option` per value.

**3. The filter stops copying and starts addressing.** It writes the *positions* that survived into a selection vector, and the second predicate reads through that selection — so the second comparison is evaluated only over survivors, and nothing is copied. That is C4.L2, and it is the part that changes the shape of every downstream operator.

There is a fourth consequence that is not a fourth mechanism: the inner loop becomes **branchless**. The comparison result is written, not jumped on. In the model, batched mode takes **192 branches** at a vector width of 2,048 where tuple mode takes **350,967** — and a branchless countable loop over a contiguous array is the only shape a compiler will auto-vectorise (C4.L5 says exactly how far that goes).

But every batch also carries a fixed cost before it reads a single row: the model charges **8 operations per batch** — a call per operator boundary, a loop-setup branch per boundary, one selection-buffer reset and one validity check. That number is the whole crossover.

---

```rust
// THE OLD MACHINE. The unit is a row, so a row has to exist, and the cost of
// deciding "is there another one" is paid per row.
trait Operator {
    fn next(&mut self) -> Option<Tuple>;   // virtual call, per row
}

// THE NEW MACHINE — lab 03's actual API. There is no Batch struct, because a
// batch is not a thing: it is a LENGTH. Every operator takes one column of a
// batch and a list of positions, and returns a list of positions.
pub fn filter(values: &[Option<i64>], pred: &Pred, input: &Sel) -> Sel;
pub fn gather(values: &[Option<i64>], sel: &Sel) -> Vec<Option<i64>>;
pub fn aggregate_batch(t: &mut GroupTable, keys: &[Option<i64>], vals: &[Option<i64>], sel: &Sel);

// Read the signatures as a cost model and three facts fall out:
//   * no operator returns a tuple, so no operator assembles one
//   * `filter` consumes positions and produces positions, so chaining two
//     predicates copies nothing (C4.L2)
//   * `aggregate_batch` takes TWO columns and one position list, so the row
//     (key, value) is never materialised at all (C4.L3)
//
// And one that is not about speed: `table` is a parameter, not a return value,
// because the hash table is the state of the QUERY, not of the batch (C4.L4).
```

## The crossover arithmetic, and the case where batching loses

Per row, the batched machine costs roughly

```
per-row work  +  8 / batch_size
```

so the fixed cost is divided by the batch size and the per-row work is what you actually optimised. Run the model down to a batch of one row and the arithmetic bites:

| batch size | batched count | vs tuple-at-a-time |
|---|---|---|
| **1** | 1,662,333 | **1.22× — worse** |
| 2 | 1,138,064 | 0.84× |
| 8 | 744,978 | 0.55× |
| 64 | 631,650 | 0.46× |
| 256 | 623,202 | **0.46× — the minimum here** |
| 2,048 | 646,242 | 0.47× |

Those are the clustered column's counts; the other two shapes have the same shape of curve. On the dial the lab offers, **8 is the smallest choice that beats tuple-at-a-time**; on a finer sweep the model crosses at 2, and the lab's own test pins the crossover at **no worse than 8** on every column shape.

Two things in that table are worth more than the headline.

**A batch of one row is strictly worse than the machine it replaced.** Not equal — worse, by 22%. It pays the whole per-batch toll 131,072 times *and* does the per-row work, so you have bought a volcano engine and given it paperwork. This is the sentence that makes "different machine" more than rhetoric: an optimisation degrades toward the thing it optimised, and this does not.

**Bigger is not monotonically better.** The count bottoms out at 256 on this column and rises again by 2,048. The reason is mechanism 2: a wider vector is *less likely to be entirely valid*, and one null anywhere in the vector costs the whole vector its one-check shortcut. Null checks on this column go 4,352 at a width of 64 to 32,832 at 2,048. On a column with no nulls at all nothing pulls the other way, and the widest vector does win. So "what is the right vector size" has no answer that is independent of the data — which is why the lab makes you find the minimum on two different columns and get two different answers.

_fig 1 — the same query, two machines, and the batch size where the new one loses_

Components: count(*), sum(v) where v between 300 and 700 (131,072 rows · one column · three operators) · tuple-at-a-time (the unit of work is one row) · 393,216 virtual calls (350,967 branches · a null check per row) · 1,361,445 operations (10.39 per row, almost all bookkeeping) · batch-at-a-time (the unit of work is a vector) · 192 branches at width 2,048 (one validity check for the whole vector) · 646,242 operations (4.93 per row · overhead share 0.08%) · width 1: 1,662,333 operations — 1.22× tuple-at-a-time (the fixed 8-operation toll paid 131,072 times: a volcano engine carrying paperwork) · every width returns 53,259 rows and sum 25,934,662 (the answer is not a variable — it is checked against an independent reference)

Steps:
1. One query over one column of 131,072 rows, executed two ways. The data, the predicate and the answer are fixed; the only variable is what an operator considers a unit of work.
2. The row-at-a-time machine pays its overhead per tuple: three calls across operator boundaries, a has-next branch, a validity check, a branch per comparison, and a materialised tuple for every survivor.
3. Those tolls add up to 1,361,445 modelled operations, 10.39 per row, for a query whose actual arithmetic is two accumulator updates per surviving row. The bookkeeping is the workload.
4. Give every operator a vector instead and the same three tolls are charged once per batch: 192 branches instead of 350,967, one validity question for the whole vector, and a filter that writes positions rather than copying values.
5. At a vector width of 2,048 that is 4.93 operations per row and a per-batch overhead share of 0.08% — the fixed cost has been amortised into irrelevance and what remains is the work you meant to do.
6. Now set the width to 1 and the new machine is 22% WORSE than the old one, because the 8-operation-per-batch toll is now paid 131,072 times. An optimisation degrades toward what it replaced; this does not, which is what makes it a different machine.
7. And through all of it the answer never moves: 53,259 rows and a sum of 25,934,662 at every width, checked against a reference computed independently of all three modes. A fast path that changes the answer is a correctness bug with better benchmarks.

---

- **10.39 → 4.93** — modelled operations per row (Tuple-at-a-time versus batch-at-a-time at a vector width of 2,048, on the same 131,072-row column. Counts of modelled operations, not a measurement.)
- **8** — operations per batch before any row is read (A call per operator boundary, a loop-setup branch per boundary, one selection-buffer reset, one validity check. Divided by the batch size, this is the entire crossover.)
- **1.22×** — what a batch of one row costs versus tuple-at-a-time (1,662,333 operations against 1,361,445. The lab keeps 1 on the dial precisely so this can be observed rather than asserted.)
- **256** — the width that minimises the count on this column (Not the largest offered. A wider vector is less likely to be entirely valid, and a single null costs the whole vector its one-check-per-batch shortcut.)

---

> **[warning]** Execute-on-compressed (C1.L5) rides on top of the batch, and the interaction is not obvious until you set the dial wrong.
> 
> A run-length-encoded run is clipped at the **vector boundary**, because a vector is the unit an engine materialises — a run spanning two vectors is two fragments. So the compressed path's work is proportional to `runs + batches`, not to runs alone:
> 
> - **constant column, vector width 131,072:** 1 run, **1 fragment, 16 operations** for the whole 131,072-row query
> - **same column, vector width 1:** **131,072 fragments** — exactly one per row — and 2,097,152 operations
> 
> At a width of 1 the fast path is not merely diminished, it is *gone*: fragments equal rows, and the model confirms it on every column shape. On the clustered column the compressed path costs 1,361 operations at full width against the batched path's 744,042 — **more than 500× fewer**, which the lab's tests pin at over 100×. On the random column, where runs ≈ rows, it costs 724,140 against 739,901: **a wash within a few percent**, and the lab says so on screen rather than letting you generalise a win that belongs to the clustering rather than to the code.
> 
> Vector width is therefore not a tuning knob you set once. It is the parameter that decides whether two other mechanisms exist at all.

## What the lab is not, said before you draw a conclusion from it

Every number above is a **count of modelled operations** — virtual calls, null checks, comparisons, branches, selection writes, indirections, copies, allocations, arithmetic. Nothing is timed, and nothing needs to be: a count means the same thing on your laptop, in CI and in the browser tab, which is what makes these claims replayable rather than anecdotal.

What a count cannot tell you is the other half of why vectorised execution wins in a real engine:

- **Cache residency.** A vector is sized to fit in L1/L2 along with its intermediate results, so operators hand each other data that is already resident. A count of operations issued says nothing about where the operands were.
- **SIMD width.** A branchless loop over a contiguous array can retire several values per instruction. The lab counts one comparison per row either way, so it *undercounts* the batched machine's advantage.
- **Instruction-level parallelism.** No dependency chain between iterations means the pipeline stays full. Again invisible to a count.

So the honest framing: **the lab measures the work you stopped issuing, and is silent about what the memory system did with the work that remains.** It simulates an execution model; it does not measure one. What the real thing adds is everything in the list above, and C4.L5 puts a ceiling on it.

The reason this still teaches the right thing is that the mechanism the count exposes — a fixed cost per batch, amortised — is the mechanism that makes the rest possible. You cannot vectorise a loop you exit every row.

> **[vendor snapshot — verified 2026-09]** What a production vectorised engine picks for the vector, and the complexity it buys
>
> DuckDB's internals documentation states the model directly: it "uses a vectorized query execution model", all operators are "optimized to work on Vectors of a fixed size", and that size — `STANDARD_VECTOR_SIZE` — **defaults to 2,048 tuples**. That is the same order as the width where the lab's per-batch overhead share falls below a tenth of a percent, which is the arithmetic reason such a number exists rather than a preference.
> 
> The more interesting part of that page is what a vector is allowed to *be*. DuckDB documents several physical representations for the same logical data:
> 
> - **flat** — a contiguous array, the uncompressed case
> - **constant** — one value standing for the whole vector, emitted by expressions with a constant result and "also emitted by the storage when decompressing from constant compression"
> - **dictionary** — "a child vector, and a selection vector that contains indexes into the child vector", emitted when deserialising a dictionary-compressed column segment "so we can keep the data compressed during query execution"
> - **sequence** — an offset and an increment, used for row identifiers
> 
> Two things follow, and they are the durable ones. First, C1.L5's execute-on-compressed is not a bolt-on: the vector type *is* the encoded form, carried into execution rather than decoded at the storage boundary. Second, the cost is real and the docs name it: writing specialised code "for every combination of vector types for every function is unfeasible due to the combinatorial explosion of possibilities", which is why a `UnifiedVectorFormat` exists as a generic view. That is the engine-complexity price of the fast path, stated by the people paying it — and it is the same price forge lab 03 charges you when it grades the compressed path as an equivalence rather than as an optimisation.
> 
> Nothing here is a performance claim, ours or theirs. It is a design point with a number attached, and the number is a default you can change.
>
> Sources: https://duckdb.org/docs/current/internals/vector.html

_amortising a fixed cost ≡ three things you have already done_

- **batched syscalls** (One `writev` of 64 buffers instead of 64 `write` calls. The fixed cost is the boundary crossing, and the payload was never the problem — but a batch of one buffer is a plain `write` plus a struct to build.) ≡ **the vector** (One call per operator boundary per 2,048 rows instead of per row. And a vector of one row is the old machine plus a selection buffer, which is why the count goes UP at width 1.)
- **multi-row INSERT versus a loop** (Parse, plan and round-trip once for a thousand rows. Everyone knows this one, and nobody calls it "a faster INSERT" — it is a different statement.) ≡ **batch-at-a-time execution** (Plan once, cross the operator boundary once, decide validity once. The operator interface changes shape, which is what makes it a machine rather than a tuning flag.)
- **a page as the unit of I/O** (You never read a byte from disk; you read a page and use part of it. The page size is a tradeoff between per-request overhead and wasted bytes, and there is no universally right value.) ≡ **the vector width** (Exactly the same tradeoff one level up: per-batch overhead against the odds that the whole vector is uniform. The minimising width on this lab's columns is 256 on one and the full column on another.)

**Q1. A colleague reads that DuckDB uses a vector size of 2,048 and proposes making your engine's batch size configurable "so tuning it down is available if memory gets tight". What is the strongest objection?**
   A. Nothing is wrong — a smaller batch always trades a little throughput for a smaller memory footprint, and the tradeoff is smooth
   B. Below the crossover the batched engine costs MORE than tuple-at-a-time, and it degrades non-monotonically: a batch of 1 is 1.22× the tuple-at-a-time count and also collapses the compressed path from 1 fragment to one fragment per row, so "tune it down" has a cliff, not a slope
   C. The batch size cannot be changed at runtime because it is a compile-time constant in every real engine
   D. Smaller batches break the correctness of the selection vector, since positions are only valid within a batch of the standard width
   Answer: B — The curve is not a slope. It has a minimum in the middle — 256 on the lab's clustered column — rises again at very large widths because a wider vector is less likely to be all-valid, and below the crossover it goes above the machine batching replaced: 1,662,333 operations at width 1 against 1,351,892 for tuple-at-a-time. Worse, run-length fragments are clipped at the vector boundary, so a width of 1 turns execute-on-compressed into exactly one fragment per row and destroys a second mechanism entirely. Positions stay correct at every width — the answer is 53,259 rows and sum 25,934,662 throughout — so the failure is a cost cliff, not a wrong result.

**Q2. Why is "batch-at-a-time is a different machine, not a faster loop" a claim about engineering rather than a slogan?**
   A. Because vectorised engines are written in C++ and volcano engines are usually written in Java
   B. Because the operator interface itself changes: nothing returns a tuple, so a filter produces positions instead of rows, an aggregate consumes two columns and a position list, and the hash table becomes state owned by the query rather than by the batch — none of which is reachable by making the row loop tighter
   C. Because vectorised execution always produces the same answer, whereas the volcano model can differ on nulls
   D. Because a batch is a struct and a tuple is not, so the memory layout differs
   Answer: B — Read the signatures in forge lab 03: filter takes positions and returns positions, gather is the one function that copies, aggregate_batch takes two columns of the same batch plus a selection, and the group table is a parameter because it accumulates across batches. Those are different interfaces with different invariants — a selection must be strictly increasing, must be a subset of its input, and an empty selection means nothing survived rather than no filter. You cannot arrive at any of that by optimising next(). The tell is the degradation direction: an optimisation gets closer to the original when you weaken it, whereas this gets worse than the original, which means it is not on the same curve.

**Q3. You cut per-row overhead from 10.39 modelled operations to 4.93 and report a 2.1× reduction in work issued. What caveat should you state first, before anyone in the review finds it?**
   A. That the measurement was taken on one column shape and may differ on others
   B. That a count of modelled operations describes the work you stopped issuing and says nothing about cache residency or SIMD width — so it both undercounts the real win and cannot be converted into a runtime claim, and the honest number is bytes and operations, not a speedup
   C. That the answer might change under vectorised execution, so equivalence has to be tested separately
   D. That the improvement will disappear once the data is larger than memory
   Answer: B — The caveat that matters is what the metric is silent about. Counts are chosen here precisely because they are reproducible on any machine, but they price one comparison per row identically in both modes even though a branchless contiguous loop can retire several values per instruction, and they say nothing about whether the operands were in L1 or in DRAM. So the count understates the batched machine and cannot be turned into a wall-clock ratio in either direction. Option 1 is true but weak — the curve has the same shape on all three shapes. Option 3 is not a caveat here: equivalence is not assumed, it is checked against an independent reference at every row cursor, which is the one thing this model does not have to hedge.

The founding paper is **Boncz, Zukowski and Nes, "MonetDB/X100: Hyper-Pipelining Query Execution" (CIDR 2005)**. Read it for the framing rather than the numbers: it argues that the volcano model's problem is not its algorithms but its *interpretation overhead*, and that the fix is to make the unit of interpretation a vector sized to the CPU cache. **Zukowski's thesis, "Balancing Vectorized Query Execution with Bandwidth-Optimized Storage" (2009)**, is the long version and the better one on why the vector size has a sweet spot at all.

For the other side of the argument, **Kersten, Leis, Kemper, Neumann, Pavlo and Boncz, "Everything You Always Wanted to Know About Compiled and Vectorized Queries But Were Afraid to Ask" (VLDB 2018)** implements both a vectorised and a data-centric compiled engine and compares them honestly, including where each loses. It is the paper to read before asserting that either model is simply better — the answer is workload-dependent and the paper says which way, for which shapes.

For the volcano model itself, **Graefe, "Volcano — An Extensible and Parallel Query Evaluation System" (1994)** is the primary source, and **tablespace T5.L1 and T7.L2** teach it from the row store's side. Do not re-derive it here.

Two production engines worth reading as documents rather than products: **DuckDB's execution-format page** (the vendor block above) for how vector types carry encodings into execution, and the **Photon** paper (**Behm et al., SIGMOD 2022**) for a vectorised engine built to run inside an existing row-oriented ecosystem — its discussion of why they chose vectorisation over compilation, and what the adaptive fallbacks cost, is unusually candid.
