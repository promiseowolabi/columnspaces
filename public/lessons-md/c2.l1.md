# C2.L1 — Row Groups and Statistics

_Track C2: Layout & Pruning · ~18 min · columnspaces_

> The last refinement of the row-group dial multiplies your footer statistics by four and buys under five points of pruning. Both ends of that dial are traps, and only one of them is famous.
C0.L2 gave you the four levels — file, row group, column chunk, page — and C0.L4 gave you the reason one of them matters: pruning is a property of physical order, and it collapsed 39.8× when the order changed. This lesson is about the level where that decision is actually made, and about the three or four numbers the writer leaves behind so it can be made at all.

**The row group is the pruning unit.** Not the file, which is too coarse to summarise usefully once it holds two years of history. Not the page, which is where decode work is bounded but which most planners will not consult before they have already decided to fetch the chunk. The row group is the granule at which a scan says "no" — and it says it by comparing your predicate to a handful of bytes recorded per column per row group.

So the row group size is not a performance tuning knob in the usual sense. It is **the resolution of every statement your table is able to make about itself.** Two row groups over two years means the coarsest possible claim: "this half has timestamps between here and there." No predicate, however selective, can extract more than one bit from that.

---

## What the statistics actually are

Per column, per row group, a writer records a small fixed set of facts. There are four that matter and they are not equally reliable:

| fact | what it lets you prove | how much you can trust it |
|---|---|---|
| **min** | no row is below it, so `x < min` matches nothing | load-bearing. A min that is not a true lower bound is a false-negative generator |
| **max** | no row is above it, so `x > max` matches nothing | load-bearing, same asymmetry |
| **null count** | `IS NULL` is impossible at 0; `IS NOT NULL` is impossible at the row count | the one people forget, and the one that makes null predicates prunable at all |
| **distinct count** | cardinality, for join and aggregation planning | optional in every format, and usually absent. Never build a plan that requires it |

Two properties of that list carry most of the implementation weight.

**First: min and max are bounds, not values.** A conforming writer may record a *looser* bound than the truth — a lower bound below every value rather than the smallest value present. That is legal because pruning only ever needs one direction to be sound: you must never claim a block cannot match when it can. It is why string bounds are often truncated to a prefix, and why a planner that treats min as "a value that exists in this block" is wrong in a way that will eventually produce an empty result set from a non-empty block.

**Second: absent is not zero.** Statistics that were never written and statistics that record "no nulls here" are different claims with opposite consequences. Missing statistics prove nothing, so the block must be read. A recorded null count of zero proves `IS NULL` impossible, so the block is skipped. Collapse the two and you have either an inflated bill or a silently wrong answer, depending on which way you collapsed them.

## What forge lab 02 makes you prove

Lab 02 (`zone-maps`, "Learn Not to Read") is where this stops being description. You implement `column_stats`, `block_meta`, `row_matches`, `might_read` and `plan` over run-length-encoded blocks you compressed yourself in lab 01, and the harness re-derives every number with its own independent implementation before deciding anything.

`stats_exact` is the check for this lesson, and it is specific about the four traps:

- **min and max are over non-null values only**, and they are absent *together* — the harness asserts `min.is_some() == max.is_some()`, because a block that has one and not the other is a block whose metadata contradicts itself.
- **A run of count 0 holds no rows**, so it contributes nothing to min, nothing to max and nothing to the null count. The corpus includes a count-0 run below the true min and one above the true max, precisely so that summarising *runs* instead of *rows* fails.
- **`null_count` counts rows**, so a null run of count 40 contributes 40. There is a hand case with a null run of 1,000.
- **`Some(stats)` versus `None` is a claim about the writer, not the data.** The check fails a `None` with a message worth quoting: *"None means the writer recorded nothing, which forbids the planner from ever pruning this column — you computed the statistics, so record Some(..)."*

That last one is the shape of the whole lab. Being unable to prune is a bill; being *wrong* about a bound is an incident. `stats_exact` runs seventeen hand-built columns where the answer is obvious by eye, then every block of ten generated layouts through `block_meta`.

> **[vendor snapshot — verified 2026-09]** What Parquet records per column chunk, and what DuckDB writes by default
>
> **Parquet's `Statistics` struct** (in the format's Thrift definition) carries `min_value`, `max_value`, `null_count`, `distinct_count` and — for floating-point columns — `nan_count`. Every field is optional. Three details in the specification are directly load-bearing for a planner:
> 
> - `min_value` and `max_value` are documented as *bounds*, and the struct carries `is_min_value_exact` / `is_max_value_exact` flags because writers are explicitly permitted to store shorter, looser values. The spec's own example: rather than storing `Blart Versenwald III`, a writer may set `min_value = "B"`.
> - On `null_count`: writers *should* always write it even when zero, and **readers must distinguish "not present" from "== 0", and must not assume zero when it is absent.** That is the absent-is-not-zero rule, written into the format.
> - `distinct_count` exists as "count of distinct values occurring" and is optional. The older `min`/`max` fields are deprecated and defined by signed comparison only, regardless of the column's logical type.
> 
> Page-level statistics live separately, in the `ColumnIndex` / `OffsetIndex` pair, which hold per-page bound lists, per-page null counts and a `boundary_order` flag — so a reader can binary-search the pages of a sorted column instead of scanning their bounds.
> 
> **DuckDB's Parquet writer** defaults `ROW_GROUP_SIZE` to **122,880 rows** (`CHUNK_SIZE` is an alias for the same option), which is sixty of its 2,048-row vectors. `ROW_GROUP_SIZE_BYTES` defaults to `row_group_size * 1024` but is documented as only taking effect once `preserve_insertion_order` is false. `DICTIONARY_SIZE_LIMIT` defaults to `ROW_GROUP_SIZE / 5` distinct values — so the row-group dial silently moves the dictionary threshold too, which is one reason the compression side of the trade is not independent of the pruning side.
> 
> Verify these against your own writer's footer before quoting them: the *shape* of the trade is durable, the defaults are a version-specific fact.
>
> Sources: https://github.com/apache/parquet-format/blob/master/src/main/thrift/parquet.thrift · https://duckdb.org/docs/stable/sql/statements/copy.html

```sql
-- the pruning-lab fixture: 512,000 rows, four columns, written in timestamp order.
--   row groups      = ceil(rows / rows_per_group)
--   stats entries   = columns × row groups        <- one per column chunk
--   pruning ceiling = 1 - 1/row_groups            <- for a predicate inside ONE group

--   262,144 rows/group ->   2 groups ->   8 entries -> ceiling  50.0%
--   131,072 rows/group ->   4 groups ->  16 entries -> ceiling  75.0%
--    32,768 rows/group ->  16 groups ->  64 entries -> ceiling  93.8%
--     8,192 rows/group ->  63 groups -> 252 entries -> ceiling  98.4%
--     2,048 rows/group -> 250 groups -> 1000 entries -> ceiling 99.6%
--
-- the last step: 3.97× the statistics entries for 1.2 points of ceiling.

-- and this is where the counts come from — the file's own footer, not a trace:
SELECT
  count(DISTINCT row_group_id) AS row_groups,
  count(*)                     AS stats_entries,   -- one row per column chunk
  max(num_values)              AS group_rows
FROM parquet_metadata('pruning-rg-8k.parquet');

-- the planner's own input, for one column:
SELECT row_group_id, stats_min_value, stats_max_value, stats_null_count
FROM parquet_metadata('pruning-rg-8k.parquet')
WHERE path_in_schema = 'order_ts'
ORDER BY row_group_id;
```

## The dial's two edges, priced

C0.L2 named the trade: pruning precision against metadata volume and compression efficiency. Here is the arithmetic that turns it into a decision, using the numbers the pruning lab measures on real files.

**The coarse edge is a ceiling, not a gradient.** Two row groups cannot skip more than one of themselves, so 50% is the *best case* at 262,144 rows per group — for a one-day predicate against a 729-day table, which is 0.14% of the rows. The predicate's selectivity is irrelevant past that point; you have run out of resolution. This is the edge people meet when they set row groups by target file size and never check the group count.

**The fine edge has three costs and they compound.**

1. **Statistics entries scale as columns × groups.** Four columns over 250 groups is 1,000 entries against 252 at 8,192 rows per group. On C0.L2's 45-column table it was 9,000 entries — and every one of them is parsed *before* any data is read, on every query, including the ones that will end up reading everything.
2. **Footer bytes grow with the entries.** The footer is not a fixed cost you amortise; it is per-file overhead that every reader pays on open. The pruning lab reads it out of `parquet_file_metadata` where the build exposes it, and reports the statistics-entry count everywhere, because a count is available on every build and means the same thing everywhere.
3. **Compression loses its runway.** Dictionaries and runs are built within a chunk, so a chunk of 2,048 rows amortises a dictionary over 2,048 rows instead of 122,880. On DuckDB the dictionary size limit is itself derived from the row group size, so shrinking the group shrinks the dictionary it was willing to build.

**And there is a fourth cost, which is the one that surprises people: at the unselective end, finer row groups read *more bytes for the same query*.** The pruning lab grades exactly this as a task — at the two-year window, where nothing can prune on any layout, the 2,048-row file reads more bytes than the 262,144-row one. Smaller pages, more page headers, more footer, and no pruning left to pay for any of it. "Smaller row groups are better" is false at both ends of the dial and the reader can watch it be false.

So the crossover is where the ceiling stops binding. Once your row groups are fine enough that a typical predicate lands inside one or two of them, further refinement buys ceiling you cannot use and metadata you certainly pay. On this fixture that is somewhere around 8,192 rows per group — and the honest way to say it in a review is **"we sized row groups so the seven-day predicate lands in two groups; going finer costs four times the footer statistics for about a point of pruning."**

_fig 1 — the row-group dial, both edges, and the crossover between them_

Components: 512,000 rows × 4 columns (written in timestamp order) · the dial: rows per row group (one number, three consequences) · 262,144 rows/group (2 row groups) · 8,192 rows/group (63 row groups) · 2,048 rows/group (250 row groups) · ceiling 50% (selectivity stops mattering) · 98%+ pruned (the window lands in 1–2 groups) · + a couple of points (ceiling you cannot use) · 8 stats entries (4 columns × 2 groups) · 252 stats entries (parsed before any data) · 1,000 stats entries (3.97× the footer metadata) · the losing edge: a 2-year window over a 2-year table (nothing prunes anywhere, and the 2,048-row file reads MORE bytes than the 262,144-row one)

Steps:
1. One table, four columns, 512,000 rows in timestamp order — and exactly one knob turned: how many rows a row group holds. Every count below comes out of the resulting files' own footers rather than from a trace.
2. The knob sets the number of row groups, and the number of row groups is the resolution of every claim the table can make about itself. A factor of 128 in group size is a factor of 125 in how many separate min/max claims exist.
3. At the coarse end the pruning ratio is capped by arithmetic: two groups cannot skip more than one of themselves, so 50% is the ceiling for a predicate selecting a fraction of one percent of the rows. Selectivity stops mattering once resolution runs out.
4. Metadata is the price, and it scales as columns times groups: 8 statistics entries, then 252, then 1,000 — each of them parsed before a single data byte is fetched, on every query, including the ones that end up reading the whole table anyway.
5. Then the edge nobody expects. Widen the predicate until nothing can be pruned on any layout, and the finest file reads more bytes than the coarsest — smaller pages, more page headers, more footer, and no skipping left to pay for the overhead.

---

- **63** — row groups at 8,192 rows (ceil(512,000 / 8,192) = 63 on the pruning-lab fixture. Redo it with your own row count: the group count, not the group size, is what bounds pruning.)
- **252 → 1,000** — statistics entries, 8k vs 2k rows per group (Four columns × 63 groups against four columns × 250. Every entry is parsed before any data is read, so this is planning work you pay on every query.)
- **50%** — the pruning ceiling at 262,144 rows per group (Two row groups can skip at most one of themselves. A one-day predicate over 729 days cannot do better, however selective it is.)
- **4** — statistics per column chunk worth knowing (min, max, null count, and sometimes distinct count. Only the first three are reliably present, and only the first three can prune.)

That number is the one correctness claim on the page; everything else there is a bill.
> 
> Its falsifiable claim is stated so it could come out against the lesson: *"pruning follows physical clustering, and a sort key that does not match the predicate prunes nothing."* If you can find a configuration where the wrong-column predicate prunes well, the lesson is wrong and the lab will show it.

---

> **[segfault]** A block of nothing but nulls has **no min and no max**. That is a proof — no comparison can match a block with no non-null value in it — so `x > 5` prunes it correctly. It is emphatically *not* a proof about `IS NULL`, which every row of that same block satisfies.
> 
> Which means the tempting first line of a planner:
> 
> ```
> if stats.min.is_none() { return false }   // "nothing here to compare"
> ```
> 
> skips exactly the blocks `IS NULL` is looking for, and silently drops every null row in the table. Lab 02's `null_semantics` check states the case in its own failure message: *"A planner that returns early on min.is_none() skips exactly the blocks IS NULL is looking for, and drops every null row in the table."*
> 
> `IS NULL` consults the null count. `IS NOT NULL` compares the null count against the row count. Comparisons need min and max to exist first. Three branches, and they cannot be collapsed into one.

---

_a row group ≡ three things you already size_

- **a database page** (Bigger pages amortise per-page headers and read fewer of them; smaller pages waste less on a point lookup. There is no globally right size, only a right size for an access pattern.) ≡ **a row group** (Identical curve one layer up, with statistics in place of headers: the coarse edge wastes bytes, the fine edge wastes planning, and the workload picks the crossover.)
- **a histogram bucket** (More buckets mean sharper selectivity estimates and a larger catalog to maintain and read. Past a point the extra buckets change no decision.) ≡ **a row group's min/max pair** (A two-value summary per bucket, where the bucket boundaries are the write order rather than a chosen quantile — which is why they are free and also why they can go uninformative overnight.)
- **a monitoring scrape interval** (Halve it and you see finer detail and store twice the samples. Nobody argues for a one-second interval on a metric checked weekly.) ≡ **the row-group size dial** (Resolution you cannot act on is pure storage and parse cost. 250 groups where 63 already put the predicate inside two is a scrape interval nobody reads.)

**Q1. A team writes Parquet with row groups sized to 256k rows because their target file size came out neatly that way. Their dashboard filters a seven-day window over a two-year table and prunes 50%. What is the diagnosis?**
   A. Statistics are stale and need recollecting so the planner can prune again
   B. The table has only two row groups, so 50% is the arithmetic ceiling — a predicate cannot skip more than one of two blocks, and no amount of extra selectivity changes that. The fix is resolution, not statistics
   C. The predicate is not selective enough to prune further at any row-group size
   D. Compression is interfering with the min/max statistics, so the bounds are too wide to exclude anything
   Answer: B — Pruning is bounded by 1 − 1/row_groups: with two groups the best possible outcome is skipping one of them, and the fixture shows exactly that at 262,144 rows per group. Selectivity is not the constraint here — the seven-day window is under 1% of the rows and still cannot do better, because resolution has run out. Statistics are recomputed on every write and are correct; they are simply too coarse to say anything useful. Note the trap in sizing row groups from a target file size: file size is a storage decision, group count is a pruning decision, and they are not the same dial.

**Q2. A planner reads a column chunk whose metadata has no statistics entry for the predicate's column, and separately a chunk whose statistics record a null count of 0. What should it do with each, and why does the distinction matter?**
   A. Skip both: no statistics and no nulls are both proofs of absence
   B. Read both: statistics are only ever advisory, so neither case can be relied upon for a skip
   C. Read the first (missing statistics prove nothing) and, for an IS NULL predicate, skip the second (a recorded null count of 0 proves no row is null) — treating absent as zero would turn a bill into a wrong answer
   D. Skip the first (a writer omits statistics only for columns it knows are empty) and read the second
   Answer: C — Absent statistics and a recorded zero are different claims with opposite consequences, and the Parquet specification says so directly: readers must distinguish null_count not being present from null_count == 0, and must not assume zero when it is missing. Missing metadata proves nothing, so the block is read and you pay for it; a recorded zero is a proof, so IS NULL can skip the block. Collapsing the two in the "skip" direction drops every null row in blocks whose writer simply did not record the count — a silently wrong answer with no error anywhere. Lab 02 grades both cases explicitly, including metadata that has no entry for the column at all.

**Q3. To cut the daily scan bill, an engineer proposes dropping row groups from 8,192 to 2,048 rows across a 45-column table. What should you ask them to measure before the change ships?**
   A. The compression ratio, since smaller row groups compress better within each chunk
   B. The pruning ratio, and only the pruning ratio, since it is the term that drives bytes scanned
   C. The pruning ratio AND the statistics-entry count and footer size AND the bytes read by the unselective queries — because the entries grow roughly 4×, the ceiling gains about a point when the predicate already lands in two groups, and at the unselective end the finer file reads more bytes than the coarser one
   D. The wall-clock latency of the dashboard queries before and after, since that is what users experience
   Answer: C — This change is three effects, and only one of them is the improvement. Statistics exist per column per row group, so 45 columns across four times as many groups is four times the footer entries, all parsed before any data is read. The pruning gain is bounded by the ceiling the table already had — if a seven-day predicate already lands in two of 63 groups, there is roughly a point available. And the pruning lab grades the case that catches people: at a window that prunes nothing on any layout, the 2,048-row file reads MORE bytes than the 256k-row one, because page headers and footer grew and there is no skipping left to fund them. Compression moves the wrong way, not the right one: a dictionary amortised over 2,048 rows is worse than one over 122,880. Latency is the wrong instrument entirely — a wide engine absorbs the bytes, which is why cost incidents in this subject are invisible until the invoice.

---

Read **Parquet's Thrift definition** directly rather than a summary of it — `RowGroup`, `ColumnMetaData`, `Statistics`, `ColumnIndex` and `OffsetIndex` are about two hundred lines and they answer most arguments about what a planner is entitled to assume. The `is_min_value_exact` flags and the deprecation note on the old signed-comparison `min`/`max` fields are the two things most people have never read.

**Apache ORC** makes the same decomposition with a different bet: stripes instead of row groups, plus a built-in row index with an entry every 10,000 rows by default, which is a decision to spend metadata on finer skipping than Parquet's page index historically offered. Two formats, one physics, different positions on exactly the dial this lesson prices.

For the *why* of grouping rows at all, **Ailamaki et al., "Weaving Relations for Cache Performance" (VLDB 2001)** — PAX — is the ancestor: column organisation inside a page-sized unit so that reconstruction stays cheap. Modern row groups are that argument at file scale. For where the row group ends up as a scheduling unit rather than only a pruning unit, **Leis et al., "Morsel-Driven Parallelism" (SIGMOD 2014)** is the one to read next, and C4 comes back to it.

**ClickHouse** is worth a look precisely because it names the granule and makes it small: its sparse primary index stores one mark per granule of a few thousand rows, which is the fine end of this dial adopted as a default and paid for with a very different metadata layout. Whether that is right for you is a workload question, and the arithmetic in this lesson is how you answer it rather than argue about it.
