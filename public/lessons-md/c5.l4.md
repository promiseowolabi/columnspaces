# C5.L4 — Small Files and the Freshness Curve

_Track C5: The Write Path · ~18 min · columnspaces_

> Someone asks for 30-second freshness instead of 15-minute. That is one sentence in a ticket, 30× the files at identical data volume, an average file of 8.7 MB instead of 260 MB, and a compaction ladder that blows the write-amplification budget before a single row is restated.
Freshness feels like a latency requirement and behaves like a file-count decision. The conversion between them is two lines of arithmetic, and the reason it surprises people is that the two lines live in different teams' documents.

Start with what "fresh" actually measures. A row arrives at some point inside the current batch window, waits for the window to close, and becomes visible once the commit lands:

```text
staleness of one row  =  time until the next cut  +  commit time

rows arrive roughly uniformly inside the window, so:
  mean staleness  ≈  interval ÷ 2  +  commit time
  p99  staleness  ≈  0.99 × interval  +  commit time   ≈  interval + commit
```

**Quote the p99, and quote it as interval plus commit.** The mean is half the interval and is the number that makes a document look better than the system. And if the write buffer is not on the read path, add the conversion lag from C5.L2 — that is the version of this arithmetic that is off by an order of magnitude and green on a dashboard.

Now the other side. C2.L5 established that file count is a product — commits per day × partitions written per commit × writers per commit — and derived the ceiling past which files are permanently small: daily ingest ÷ target file size, about **48 actively-written partitions** at 25 GB/day and a 512 MB target. Do not re-derive that. Take the commit term and turn the interval into files:

```text
commits per day   =  1440 ÷ interval_minutes
files per day     =  commits × partitions × writers
average file size =  daily bytes ÷ files per day
```

Two lines, and between them they say something a freshness ticket never does: **the batch interval is the only free variable, and the file count is the consequence.**

---

## The curve, at 25 GB a day

One partition, one writer, so the numbers are the floor rather than a realistic case:

| batch interval | p99 staleness | commits/day | average file | passes to reach 512 MB |
|---|---|---|---|---|
| 15 min | ~15 min | 96 | **260 MB** | 1 |
| 5 min | ~5 min | 288 | 86.8 MB | 2 |
| 1 min | ~1 min | 1,440 | 17.4 MB | 2 |
| 30 s | ~30 s | 2,880 | **8.7 MB** | 2 |

Going from 15 minutes to 30 seconds is **30× the freshness and 30× the files for the same 25 GB.** Now multiply by the other two terms, because nobody ingests with one writer into one partition: six partitions and four writers is a factor of 24, so the 30-second row becomes **69,120 files a day averaging about 362 KB.** That is the small-file storm arriving as arithmetic rather than as an incident — and Column Week's second drill is the incident, with 9,600 files an hour, average file size collapsing from 240 MB to 6 MB, and planning growing from 4% to 61% of query time on a table whose data had not grown.

The last column is the part usually left out of the conversation, and it is the one that connects this lesson to the previous one. Compaction does not lift an 8.7 MB file to 512 MB in one hop; it merges with a fan-in, and each pass reads and writes every byte it touches:

```text
size gap        512 MB ÷ 8.7 MB      ≈ 59×
fan-in 8        ceil(log8 59)        =  2 passes
rewrite bill    2 × 25 GB/day        =  50 GB/day written for 25 GB/day ingested
write amp       1 (ingest) + 2       =  3.0×
```

**3.0× exceeds the 2.60× write budget from C5.L3 before a single row has been updated.** At the 15-minute interval the same ladder is one pass and 2.0×, comfortably inside it. So the freshness requirement is not merely a file-count decision — it consumes the same write-amplification budget your update path needs, and the two requests arrive from different teams who have never seen each other's numbers.

---

## The bound that has no steady state

File size is a cost. The *rate* is a stability condition, and it is the difference between a platform that is expensive and one that degrades:

```text
merge rate  ≥  creation rate      or the backlog is UNBOUNDED

the drill:   9,600 files/hour created
              5,000 files/hour merged
deficit:      4,600/hour  =  110,400/day
backlog:      940,000 files  ≈  8.5 days of deficit
```

No cluster size fixes a deficit, because a deficit is not a queue that saturates — it accumulates. That is why the ingest desk grades `compaction_keeps_up` as a rate against a rate, and it is why the honest form of a compaction plan is *"sized at 1.2× the observed creation rate"* rather than *"we run compaction nightly"*.

Three practical consequences, each of which belongs in a runbook rather than in someone's memory.

**Compaction cannot merge across a partition boundary.** A file belongs to exactly one partition, so the ceiling from C2.L5 is a hard floor on achievable file size: if the data to fill a 512 MB file does not exist inside the boundary in a day, no policy, cluster or vendor produces one. Check the partition scheme against the interval *before* promising a file size.

**The creation side has three levers and you own the cheapest one.** Interval, partitions written, writers. Halving the interval doubles files; adding a partition column multiplies them by its cardinality; adding a writer multiplies by the writer count. The interval is usually the only one that can move without a data migration, which is why it is the input variable and everything else is consequence.

**Small files cost counts, not bytes.** C3.L4 measured the byte penalty of small files as modest — under 1.2× from coarsest to finest layout — while the file count rose more than 10×. Planning enumerates files and reads their footers, so it scales with count; on a per-byte-scanned bill this cost is nearly invisible, which is C0.L5's trap in its purest form. If your platform charges per request, the same count becomes a line item you can point at.

> **[vendor snapshot — verified 2026-09]** One engine turns this bound into a hard error instead of a slow decay
>
> **ClickHouse** makes the creation-versus-merge condition explicit, and it is worth studying regardless of whether you run it, because it is the only mainstream engine that refuses to let you lose this argument quietly. Two MergeTree settings, both scoped to a single partition:
> 
> - `parts_to_delay_insert` — *"If the number of active parts in a single partition exceeds the `parts_to_delay_insert` value, an `INSERT` is artificially slowed down"*; the docs are explicit about the purpose: ClickHouse *"artificially executes `INSERT` longer (adds 'sleep') so that the background merge process can merge parts faster than they are added."*
> - `parts_to_throw_insert` — exceed it and the insert is *"interrupted with the `Too many parts (N). Merges are processing significantly slower than inserts` exception."*
> 
> That is backpressure and then refusal: the engine protects read performance by degrading and then failing the write path, rather than letting the part count grow until queries collapse. Compare it with a data-lake table, where the same imbalance produces no error at all — just a backlog, a rising planning share, and an invoice. The documentation also names the tuning trap directly: raising the throw threshold *"will reduce the probability of the `Too many parts` error, but at the same time `SELECT` performance might degrade"*, and a merge problem such as insufficient disk space will be noticed later than it would have been. The docs note the setting was 300 prior to version 23.6; read the current value out of `system.merge_tree_settings` rather than trusting any number in a course.
> 
> **Iceberg** has the target but not the refusal: `write.target-file-size-bytes` defaults to 536870912 (512 MB) and describes files *"generated to target about this many bytes"* — a target the writer aims at with whatever data it has been handed. Nothing in the format prevents you from committing every thirty seconds into two hundred partitions, and nothing errors when you do.
> 
> **The design lesson, which is the transferable part:** an ingest configuration that violates the rate condition is a bug, and platforms differ only in whether they tell you. If yours does not, the alarm is yours to build — files created per hour against files merged per hour, on one axis, with the crossing as the alert rather than the backlog level.
>
> Sources: https://clickhouse.com/docs/reference/settings/merge-tree-settings/parts-to · https://iceberg.apache.org/docs/latest/configuration/

_fig 4 — one ticket asking for freshness, and the four numbers it silently sets_

Components: batch interval (the only free variable in the system) · + commit time (and conversion lag, if the buffer is not readable) · = p99 staleness (the mean is half of this, and flatters the design) · files/day = (1440 ÷ interval) × partitions written × writers — three multiplicands owned by three different teams (15 min → 30 s is 30× the files at identical data volume; six partitions and four writers multiplies that by another 24) · average file: 260 MB → 8.7 MB (and 362 KB once the partition and writer terms are included) · planning enumerates files, so it scales with COUNT (the drill measured 4% → 61% of query time while bytes barely moved) · merge rate ≥ creation rate, or the backlog is unbounded: 9,600 created vs 5,000 merged per hour is 110,400/day of deficit (a deficit accumulates rather than saturating, so no cluster size fixes it — and the size gap costs 2 compaction passes, which is 3.0× write amplification) · so the runbook states four numbers: interval, target file size, p99 staleness, compaction capacity — and which side you gave up (exactly what ingest-desk grades as freshness_sla, file_size, compaction_keeps_up and tradeoff_stated)

Steps:
1. Freshness is the interval plus the commit, at p99 rather than at the mean — and if the write buffer is not on the read path, plus the conversion lag, which is the version that is off by an order of magnitude.
2. The same interval appears in the file-count product, alongside partitions written and writers per commit — three multiplicands set by three different teams, none of whom owns the product they make.
3. So thirty times the freshness is thirty times the files at constant data: a 260 MB average becomes 8.7 MB, and about 362 KB once six partitions and four writers are included in the multiplication.
4. And the cost of that lands on planning rather than on bytes, because planning enumerates files and reads their footers: the drill measured it going from 4% to 61% of query time while the data volume was flat.
5. The binding constraint is a rate against a rate. A deficit of 4,600 files an hour is 110,400 a day and does not saturate, which is why the 940,000-file backlog in the drill was about 8.5 days old rather than steady.
6. And the ladder back to a usable file size costs two full passes over every ingested byte, which is 3.0× write amplification — already outside the 2.60× budget the update path was given in the previous lesson.
7. Which is why the deliverable is four numbers and a named loser rather than an SLA: interval, target file size, p99 staleness, compaction capacity, and which of them you chose not to promise.

---

- **interval + commit** — p99 staleness, and 1 number to quote (Rows arrive roughly uniformly inside a window, so the mean is about half the interval. Quoting the mean is the most common way a freshness claim is technically true and operationally wrong.)
- **8.7 MB** — average file at a 30-second interval, 25 GB/day (One partition and one writer, so it is the floor. Six partitions and four writers multiplies the file count by 24 and takes the average to about 362 KB.)
- **3.0×** — write amplification of the compaction ladder alone (Two passes at fan-in 8 to close a 59× size gap, so 50 GB/day rewritten for 25 GB/day ingested. That is already outside C5.L3's 2.60× budget before any row is updated.)
- **110,400/day** — file deficit when merges trail creations (9,600 created against 5,000 merged per hour, from Column Week's second drill. A deficit accumulates rather than saturating, which is why the 940,000-file backlog was 8.5 days of arithmetic.)

> **[analogy]** The request arrives as *"can we get 30-second freshness on this table?"* Neither "yes" nor "no" is a professional answer. This is:
> 
> > "Yes, at a stated cost, and here it is. Thirty-second batches on this table means about 2,880 commits a day instead of 96, so at six partitions and four writers that is roughly 69,000 files a day averaging under half a megabyte. Closing the gap back to a 512 MB target costs two compaction passes — about 50 GB rewritten per day for 25 GB ingested, which is 3.0× write amplification against the 2.60× we budgeted for the update path — and compaction has to sustain the new creation rate with headroom, or the backlog grows without bound and planning cost rises the way it did in INC-2. The alternative I would recommend is a five-minute interval with the write buffer on the read path: p99 staleness lands near five minutes, files average about 87 MB, and the ladder is the same two passes but on 24× fewer files. If the 30-second number is a hard requirement, the thing to change is not the interval but where the query reads from — and that is a platform decision rather than a configuration one."
> 
> Four properties make that answer work, and they are the same four every time: it gives both numbers rather than an opinion; it names the budget the request consumes and who else was spending it; it offers a cheaper point on the curve with its own numbers; and it says which decision is above its own pay grade. The person asking for freshness is not wrong to want it — they simply cannot see the file-count product from where they sit, and it is your document that makes it visible.

---

_the freshness curve ≡ curves you already price_

- **batch size in a message consumer** (Smaller batches lower latency and raise per-batch overhead — acknowledgements, round trips, fixed costs paid per batch rather than per message. The optimum is a function of the fixed cost, not a preference.) ≡ **the batch interval** (Same shape with the fixed cost being a file: a footer, a metadata entry, an object-store request, and a slot in every planner's enumeration. That is why the penalty shows up in counts rather than in bytes.)
- **a checkpoint interval** (Checkpoint often and recovery is fast while steady-state overhead is high; rarely and the reverse. Nobody expects one setting to win both, and the deliverable is a stated RPO with the overhead it costs.) ≡ **the compaction cadence** (Identical trade, and the same discipline: state the read amplification you are holding and the write amplification you are spending, because a cadence without a budget is an unbounded background bill.)
- **a producer/consumer rate imbalance** (If producers outpace consumers, the queue grows without bound and no amount of consumer capacity fixes a deficit — you either slow the producer or fund the rate, and backpressure is how a well-built system tells you.) ≡ **file creation versus compaction** (Exactly the same condition. One engine implements backpressure and then refusal for precisely this reason; a data-lake table implements neither, so the alarm on the crossing is your responsibility.)

**Q1. A product team asks to move a table from 15-minute batches to 30-second batches. The table ingests about 25 GB/day across 6 partitions with 4 writers, targets 512 MB files, and the update path has a stated write-amplification budget of 2.60×. What is the defensible response?**
   A. Approve it and increase compaction compute proportionally, since the data volume is unchanged and only the file count moves
   B. Quote the consequences as counts and offer a cheaper point on the curve: 30× the commits means roughly 69,000 files a day averaging under half a megabyte, the ladder back to 512 MB is two passes at about 50 GB/day rewritten — 3.0× write amplification, already over the 2.60× budget the update path was given — and compaction must sustain the new creation rate with headroom or the backlog is unbounded. Recommend a 5-minute interval with a queryable buffer, and escalate 30 seconds as a platform decision
   C. Decline it: 30-second freshness is not achievable on a columnar table because files cannot be written that quickly
   D. Approve it but partition by hour instead of by day, so that each query touches fewer of the new small files
   Answer: B — The request is legitimate and the answer is a priced counter-offer. Every number in the correct option is arithmetic the asker can redo: commits per day from the interval, files from the product, average size from daily bytes divided by files, passes from the size gap and a fan-in, and rewrite bytes from the passes. The important move is naming the *shared* budget — the compaction ladder alone consumes more write amplification than the update path was allocated, which turns a freshness request into a visible collision between two teams. Adding compaction compute treats a structural cost as a capacity problem and leaves the write-amp budget silently blown. Declining is wrong on the physics: 30-second commits are entirely possible and merely expensive. And hourly partitioning divides the same data by another 24, making average file size worse while only helping queries whose predicate matches the partition key.

**Q2. A design document states: "batches commit every 10 minutes, so data is at most 10 minutes old." Queries read only compacted files, and the conversion job runs every 20 minutes. What is wrong, and what should the document say?**
   A. Nothing is wrong — 10 minutes is the correct upper bound, since every row is committed within one interval
   B. Two errors. p99 staleness is interval plus commit time rather than the interval alone, and because the buffer is not on the read path the conversion lag dominates: visibility is roughly 20 minutes plus a run, not 10. The document should state p99 staleness as a measured outcome — the age of the newest visible row under load — rather than deriving a bound from an input
   C. The document should quote mean staleness of 5 minutes, since averaging over arrival times is the standard way to express freshness
   D. The interval should be described as a target rather than a guarantee, because commit times vary under load
   Answer: B — Both errors are common and they compound. The first is quoting an input as an outcome: staleness for a row is the wait until the next cut plus the commit, so p99 is close to a full interval plus commit rather than the interval alone. The second is larger and structural: if queries cannot see the buffer, visibility waits on conversion, so the honest figure here is dominated by a 20-minute job the document does not mention. Quoting the mean instead makes the number smaller and less useful — a freshness claim exists to bound the worst case an analyst will experience. Softening "guarantee" to "target" is a wording fix for a measurement problem, and the fix is a write-then-read probe graphing the age of the newest visible row.

**Q3. Compaction merges about 5,000 files an hour; ingest creates about 9,600. The backlog is 940,000 files and planning is 61% of query time. Which plan is sound?**
   A. Double the compaction cluster and leave ingest alone, since 10,000 merged against 9,600 created clears the deficit and the backlog will drain on its own
   B. Do both, in this order: raise the batch interval to the largest value the freshness SLA permits — that lowers creation rate proportionally and is the only lever that does not need a data migration — then size compaction at a stated multiple of the observed creation rate with headroom, and alarm on the crossing of created-per-hour against merged-per-hour rather than on the backlog level
   C. Leave the rates alone and raise the query timeout, since the data volume is unchanged and planning cost is a client-side concern
   D. Disable statistics collection during ingest so that files are cheaper to create and the backlog matters less
   Answer: B — Matching rates is necessary and insufficient: at 10,000 against 9,600 the deficit stops growing but 940,000 files still need clearing, and the margin is thin enough that any ingest spike restarts the accumulation — which is why capacity is sized as a multiple of the creation rate rather than to parity. The order matters because the creation side is the cheap lever: the interval is an input variable you can change today, while partitions and writers usually imply migration. The alarm choice is the operational half of the answer — the crossing happens weeks before the backlog is visible, so alerting on level tells you when it happened rather than that it is happening. Raising the timeout hides the symptom, and dropping statistics attacks the mechanism that makes pruning possible in order to make the files that cannot be pruned cheaper to produce.

---

The reason a small file is expensive is that a *file* has a fixed cost, and the literature on that predates data lakes by decades.

For the metadata side, the canonical reference is still the **Hadoop-era work on the NameNode and small files**: a fixed metadata footprint per file, held in a single coordination service, with query planning enumerating it. The lesson survived the migration to object storage in a changed form — the coordination service became a catalog and a manifest tree — and **C3.L3** is where you read what replaced it. What did *not* survive is the assumption that listing is cheap, which is why Iceberg exists.

For the request side, **C0.L3's** request-versus-bandwidth split is the physics: object storage charges per request and delivers bandwidth per connection, so a thousand small files and one large file with the same total bytes are not the same purchase. The **object-store performance guidance** from any major provider says the same thing in operational language — request rate is a first-class dimension, and prefix design and object size are how you manage it.

For the streaming side, the honest framing is that this curve is a **micro-batch artefact**, and the systems literature has two escapes from it. The first is a queryable buffer, which is C5.L2 and is what makes a five-minute interval feel like five seconds to a reader. The second is changing the unit of storage so that a small commit is not a small file — which is what any architecture with a small chunk size is claiming, and the reason the previous lesson's arithmetic has to be redone rather than assumed on such a platform. **Kreps' work on the log as an integration abstraction** is worth reading here for the opposite reason: it argues that the log is where freshness belongs and the table is where analysis does, which is the "land the change log, materialise the state" answer this track keeps arriving at.

For the operational half, the **SRE material on leading versus lagging indicators** applies exactly: creation-versus-merge rate is the leading indicator, backlog level is lagging, and the invoice is the worst detector of both. That is the same argument C2.L6 made for clustering depth, and it is not a coincidence — every failure in this track is a slow crossing that nothing errors on.
