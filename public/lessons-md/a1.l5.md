# A1.L5 — Ingest Topologies and What Freshness Costs

_Track A1: Solution Architecture · ~19 min · columnspaces_

> Someone will say "real-time" in the meeting and mean four different architectures. Three of them are the same curve at different points, and the fourth is priced on an axis nobody in the room has mentioned.
Lead with the number, because you will be interrupted before the second slide.

**Batch, micro-batch and streaming are one curve with three names, and the curve has two axes: p99 staleness ≈ batch interval + commit time, and files per day = commits per day × partitions written × writers.** Freshness is bought with commits, commits are paid for in files, and files are what the planner reads before it reads any data. CDC is not a point on that curve. It is a fourth topology whose distinctive cost is that it is *update-heavy*, which lands on the write path you priced in C5 — and at 1% of rows changed daily with no locality, that costs about **100 bytes written per byte of change**.

Four topologies, one table, one arithmetic. Take 25 GB/day landing in 6 partitions per commit from 4 writers — the C5.L4 case — and quote average file size as daily bytes ÷ commits so the numbers are comparable, then multiply by the partition and writer terms separately:

| topology | interval | p99 staleness | commits/day | avg file (÷ commits) | files/day at 6 × 4 |
|---|---|---|---|---|---|
| nightly batch | 24 h | ~24 h | 1 | 25 GB | 24 |
| hourly batch | 1 h | ~1 h + commit | 24 | 1.04 GB | 576 |
| micro-batch | 5 min | ~5 min | 288 | 87 MB | 6,912 |
| "streaming" | 30 s | ~30 s | 2,880 | 8.7 MB | 69,120 |
| CDC | source-driven | source lag + interval | as above | as above | as above **plus delete files** |

Redo every cell: commits/day is 86,400 ÷ interval-seconds, average file is 25 GB ÷ commits, files/day is commits × 6 × 4. Nothing in that table is a benchmark; it is division. → **C5.L4** derives the freshness curve and the compaction ladder in full, and **C2.L5** derives the 48-partition ceiling past which files are permanently small. Do not re-derive either. Your job in this lesson is the *choice*, and the choice is a sentence you have to be able to say without notes.

---

## What each topology actually buys, and the loser each one names

**Batch** is the only topology where you control file size directly, because the whole window's data is in hand when the writer opens the file. That is a real architectural advantage and it is usually stated as a limitation. A nightly load produces files at the size you asked for, one commit, twenty-four files, nothing for compaction to do. What it starves: anything that needs to see today's data today, and any consumer whose SLA is shorter than the window.

**Micro-batch** is batch with a shorter window and no other difference in mechanism. File size stops being a setting and becomes a *consequence* of the interval, the partition count and the writer count — three multiplicands owned by three different teams, none of whom owns the product. What it starves: your compaction budget, quietly, because the interval is the one term that can be changed in a config review without anyone computing the file count.

**Streaming** into a columnar table is micro-batch where somebody else chose the interval. There is no per-row commit into Parquet or into an Iceberg snapshot: rows accumulate in a buffer and are committed in groups, because the unit of visibility is a file plus a metadata commit. So the honest question in the room is never "can we stream this" — it is **"what is the commit interval, and who owns it"**. What it starves: the ability to reason about file size at all, if the answer is "the framework decides".

## CDC: the topology priced on a third axis

**CDC is different in kind.** The other three append; CDC replays a source system's change log, which is dominated by updates and deletes. The freshness arithmetic still applies — you inherit the source's replication lag *plus* your own interval — but the cost that decides the design is on the write path:

```text
table            2e9 rows in 4,000 files      (500,000 rows/file)
change rate      1%/day                       = 20e6 changed rows/day
uniform locality expected files touched
                 = F × (1 − (1 − 1/F)^C)      saturates at F once C ≳ 5F
                 here C/F = 5,000, so         ≈ all 4,000 files
copy-on-write    2e9 rows rewritten for 20e6 rows of change
                 write amplification          ≈ 100×
```

Now change one thing — not the change rate, the *locality*. If the changed rows are confined to the last 7 days of a 730-day table and the layout is clustered on that key, the changes touch about 0.96% of the files, so **38 files, ~19e6 rows rewritten for 20e6 rows of change: about 1×.** Same 1% change rate, same engine, same format. **A hundredfold difference in the write bill, decided entirely by where the changes land relative to your physical layout.**

That is the sentence to bring into the room: *the cost of CDC is not the change rate, it is the change locality* — and locality is a property of your layout design (A1.L2), not of the connector.

Merge-on-read moves that cost rather than removing it: instead of rewriting 4,000 files you write delete files and pay on every read until compaction reconciles, which is exactly the read-versus-write amplification tradeoff C5.L3 priced across thirty policies — where four satisfied both constraints under an append workload and **none of the thirty satisfied both under a heavy restatement stream.** If CDC lands on a table whose compaction policy was sized for appends, the policy is void, and that is a statement you make *before* the connector is switched on.

---

- **interval + commit** — p99 staleness, never the mean (The mean is interval ÷ 2 + commit, roughly half the p99. Quoting the mean is the most common way a freshness promise is technically true and operationally wrong. Add conversion lag if the write buffer is not on the read path.)
- **69,120** — files/day at a 30-second interval (2,880 commits × 6 partitions × 4 writers, averaging 8.7 MB against a 512 MB target. Identical data volume to the nightly load that produced 24 files.)
- **100× vs 1×** — CDC write amplification, uniform versus clustered locality (The same 1% daily change rate on the same table: 20e6 changed rows rewrite all 4,000 files when spread uniformly, or 38 files when confined to recent partitions the layout is clustered on.)
- **1.2×** — merge-rate headroom the ingest desk requires (Merge rate ÷ creation rate must exceed 1.2. At parity the deficit stops growing but any spike restarts the accumulation, and a deficit is an integral rather than a queue — no cluster size fixes it.)

_fig 1 — one curve, four names, and the axis CDC is priced on_

Components: batch (24 h · 24 files/day) · micro-batch (5 min · 6,912 files/day) · "streaming" (30 s · 69,120 files/day) · CDC (update-heavy) · axis 1 — p99 = 0.99 × interval + commit (plus conversion lag if the buffer is off the read path; the mean is half of it and flatters the design) · axis 2 — files/day = commits × partitions × writers (halving the interval doubles the file count at constant data volume) · average file = daily bytes ÷ files/day: 25 GB → 1.04 GB → 87 MB → 8.7 MB against a 512 MB target (file size is a consequence of the interval, not a setting — and compaction pays the difference at 1 + passes write amplification) · axis 3, CDC only — files touched = F × (1 − (1 − 1/F)^C): 20e6 changes over 4,000 files touches all of them (copy-on-write ≈ 100× write amplification with uniform locality, ≈ 1× when the changes land in partitions the layout is clustered on) · merge rate ≥ creation × 1.2 (a deficit accumulates rather than saturating) · four numbers the ingest desk grades (p99 · achieved file size · rate headroom · the loser) · so the answer is a priced counter-offer, never yes or no: this interval, this file size, this rewrite volume, and the side we did not promise (and if CDC lands on this table, the compaction policy sized for appends is void — say that before the connector is switched on)

Steps:
1. Four names arrive in the meeting as four architectures, and the first useful move is collapsing three of them into one curve: batch, micro-batch and streaming differ only in the commit interval and in who chose it.
2. The first axis is what freshness you bought, quoted at the p99 rather than the mean: 0.99 × interval plus commit time, plus conversion lag whenever buffered rows are not visible to readers until they are converted.
3. The second axis is what it cost, and it is a product rather than a number: commits per day times partitions written times writers, which means halving the interval doubles the file count without one extra byte of data arriving.
4. Divide the daily volume by that product and file size stops being a setting you configure: the same 25 GB a day lands as one-gigabyte files or as 8.7 MB files, and compaction rewrites every byte again to close the gap.
5. CDC adds a third axis the other three do not have, because it restates rows rather than appending them: what matters is how many files the changed rows touch, and once the change count exceeds roughly five times the file count, the answer is all of them.
6. Then the binding constraint on all four: compaction has to merge faster than ingest creates, with headroom, because a deficit is an integral rather than a queue and no cluster size recovers from it once it has been accumulating for a month.
7. Which is why the deliverable is a priced counter-offer with a named loser rather than a yes: here is the interval, the file size it achieves, the rewrite volume it implies, and the side of the tradeoff we chose not to promise.

---

> **[warning]** **The buffer is not on the read path.** Every number above assumes a committed row is a visible row. If the ingest path buffers rows and converts them to columnar form on a separate schedule, the reader's staleness is interval + commit + **conversion lag**, and the conversion lag is frequently larger than the interval you spent the meeting tuning. A ten-minute SLA becomes twenty minutes plus a run, and the ingest dashboard stays green because it is measuring commits rather than visibility. The ingest desk applies this term only when you tell it the buffer is off the read path, which means the question you must ask the platform team is: *can a query see a row before the converter has run?*
> 
> **The target file size is unreachable.** A file belongs to exactly one partition, so the largest file the scheme can produce is bounded by daily ingest ÷ partitions actively written — the C2.L5 ceiling. Configure a 512 MB target on a partition receiving 40 MB a day and you have written a wish into a config file. State the average you expect to *achieve* beside the target you configured; the desk fails a target it can prove unreachable even when every other number is plausible.
> 
> Both failures share a shape worth naming out loud: the metric being monitored is upstream of the metric that was promised.

> **[vendor snapshot — verified 2026-09]** What a CDC stream actually lands on: Iceberg's three delete encodings, and one vendor claim that attacks the unit of rewrite
>
> **Iceberg, from the table spec.** Row-level deletes arrived in format **v2**, whose stated purpose is to *"delete or replace individual rows in immutable data files without rewriting the files"*. There are two kinds, and the difference is exactly the difference between a cheap CDC apply and an expensive one:
> 
> - **Position deletes** mark a row by data file path and row position. Cheap to apply at read time, but the writer must know the position — which means it has to *read the data first* to find the row it is deleting. Position delete files are **deprecated in v3**, replaced by **deletion vectors**: a Roaring-bitmap-per-data-file blob stored using the Puffin `deletion-vector-v1` type, with at most one deletion vector per data file in a snapshot, and writers required to merge new deletes into the existing vector.
> - **Equality deletes** mark a row by column values — `id = 5` — and the spec notes that engines using them *"avoid reading existing data before writing changes"*. That is why streaming CDC connectors reach for them: the write is cheap. The costs land elsewhere. An equality delete applies to every data file in the partition with a *strictly lower* data sequence number, so its read-side cost grows with the files it might apply to; equality deletes written with an unpartitioned spec are applied as **global** deletes; and the v3 row-lineage section states plainly that lineage is not tracked for rows updated via equality deletes, which are *"treated as if the existing row was completely removed and a unique new row was added"*.
> 
> Read that as an architecture statement rather than a feature list: **the CDC apply strategy is a choice about which side of the read/write amplification tradeoff pays, and the format gives you three points on it.** The 100× arithmetic above is the copy-on-write end. Deletion vectors and equality deletes are the merge-on-read end, and they defer the cost to reads plus compaction rather than removing it.
> 
> **And the claim that attacks the premise.** VAST's feature page, under *Self-Maintaining*, describes *"Write-in-Free-Space Eliminates Compaction"*: updates *"create new 32KB columnar chunks with metadata links rather than rewriting entire files, while deletions use logical tombstoning"*, which it says *"eliminates the 'small files problem' that plagues object storage systems"*. Those are VAST's words about VAST's architecture, on VAST's configuration; **no figure in this lesson is measured on it, and neither the 100× nor the 1× is theirs.** The mechanism is worth taking seriously precisely because it changes the arithmetic's unit: if the unit of rewrite is a 32 KB chunk rather than a 512 MB file, then "files touched by a change" — the quantity that produced the hundredfold spread above — is no longer the quantity that decides the bill.
> 
> **What would settle it, since we cannot run it.** For an ingest decision specifically, a proof-of-concept has to report: the cost of applying your real change stream at your real locality, measured as bytes and requests rather than seconds; storage held ÷ live bytes across a fortnight of restatement, because logical tombstoning defers reclamation rather than removing it; and the cost of updating a year-old row against one written this hour, which is the single most diagnostic measurement in the list. A1.L7 turns that list into the memo section `the-vendor` grades.
>

## Choosing, in five questions you can ask in the meeting

The topology is not chosen from taste; it falls out of five answers, and four of them are numbers somebody already has.

1. **What is the freshness requirement at the p99, and who is the consumer?** If the answer is "the dashboard refreshes hourly", the interval is bounded below by nothing and you should take the largest interval the consumer accepts. An SLA nobody consumes is a cost with no beneficiary.
2. **Can a query see a buffered row?** If not, the conversion lag goes into every promise you make, and it is frequently the dominant term.
3. **How many partitions does a commit write, and how many writers commit?** Those two multiply the interval's effect on file count directly, and they usually cannot change without a data migration — so they are constraints, while the interval is the free variable.
4. **Is the stream append-only or restating?** If restating, get the change distribution by key before discussing intervals at all. The 100×-versus-1× spread is decided here and nowhere else.
5. **What merge capacity exists, as files per hour?** Compare it against creation rate × 1.2. If it does not clear, the design is already failing and no interval choice fixes it — the arithmetic is telling you to change the partition scheme or the merge capacity.

The output is four numbers for the runbook — **batch interval, target file size, p99 staleness, compaction capacity** — plus the sentence that makes them a decision rather than a configuration: which side you gave up. That is exactly what the ingest desk grades.

---

**Desk: The Ingest Desk** — Take the topology decision into the ingest desk as four numbers, and know what each one is graded on before you submit. freshness_sla — the p99 you are promising, stated as 0.99 × interval + commit time, with conversion lag added if buffered rows are not visible to readers; submit the mean by mistake and the desk names it, because the mean is roughly half the p99 and the SLA is what the unluckiest row experiences. file_size — the target you configured beside the average you will actually achieve, where the average is daily bytes ÷ (commits × partitions written × writers); a target exceeding daily ingest per partition is unreachable by any schedule and fails here on its own. compaction_keeps_up — a rate against a rate with headroom: merge files/hour ÷ creation files/hour must clear 1.2×, because a deficit accumulates rather than saturating, and the alarm belongs on the crossing of created-per-hour against merged-per-hour rather than on the backlog level. tradeoff_stated — which side you gave up, by how much, and the write-amplification budget it consumes, expressed as bytes rewritten per byte ingested; a submission with a fresh SLA, a large target file size and no rate arithmetic fails even when every individual number is plausible, because the omission is what makes it unfalsifiable. Grading is in bands, generous to an honest model and unforgiving of a round number with no derivation behind it. If your topology is CDC, bring the locality figure with you: the change rate alone does not determine the write cost, and the desk's write-amp band will not save a design whose changes touch every file in the table.

Decision: Which ingest topology meets the freshness requirement without creating a small-file problem?
You submit: batch interval, target file size, p99 staleness, compaction capacity
Graded: freshness_sla, file_size, compaction_keeps_up, tradeoff_stated

_an ingest topology ≡ three things you already run_

- **a filesystem journal commit interval** (Shorter intervals lose less on a crash and cost more in metadata writes. Nobody calls a five-second commit "real-time journalling"; they call it a durability setting with a write cost.) ≡ **the batch interval** (Identical structure, and the honest vocabulary transfers: an interval is a durability-and-freshness setting whose price is a file count. → tablespace T0.L2 for the underlying random-versus-sequential cost model.)
- **a read replica lagging its primary** (You inherit the primary's transaction rate and the replication lag, and you cannot promise a freshness figure tighter than the lag you were handed. Everyone accepts that the lag is measured, not chosen.) ≡ **CDC staleness** (CDC is replication with a format change at the end, so the p99 you can promise is source lag plus your own interval plus commit — three terms, two of which belong to someone else's system.)
- **an LSM tree's memtable flush size** (Flush too often and you create small SSTables that compaction must merge; the write amplification is the price of the flush rate, and it is a standing cost rather than a project.) ≡ **the small-file ladder** (The columnar version has one extra sting: a file belongs to exactly one partition, so the partition scheme puts a hard ceiling on achievable file size that no policy, cluster or vendor can lift.)

**Q1. A team is switching a table from nightly batch to a CDC stream from the operational database. The source changes about 1% of the 2 billion rows each day; the table is 4,000 files of roughly 500,000 rows; the compaction policy was sized for appends. Which analysis do you bring?**
   A. The change volume is small — 1% of rows — so the ingest cost is roughly 1% of a full reload and the existing compaction policy has ample headroom
   B. Twenty million changed rows spread over four thousand files touches essentially every file, so copy-on-write rewrites the whole table daily at roughly 100 bytes written per byte of change; the number to establish first is the change distribution by key, because the same 1% confined to recent partitions we are clustered on touches about 38 files and costs near 1×, and either way the append-sized compaction policy has to be re-derived
   C. Switch the table to merge-on-read, which removes the rewrite cost and makes the change rate irrelevant
   D. Increase the compaction cluster size so the additional rewrite volume is absorbed without changing the ingest design
   Answer: B — The change *rate* is not the cost; the change *locality* is, and the ratio between the two extremes here is about a hundredfold on identical inputs. Option one is the specific mistake this lesson exists to prevent: it reasons about rows changed rather than files touched, and once the change count exceeds roughly five times the file count, uniformly distributed changes touch every file. Merge-on-read moves the cost to reads and to compaction rather than removing it — C5.L3 measured thirty policies under a heavy restatement stream and none satisfied both amplification constraints. And adding compaction capacity treats a structural rewrite volume as a capacity problem while leaving the write-amplification budget silently blown.

**Q2. Your runbook promises "5-minute freshness" for a table on a 5-minute micro-batch, and the ingest dashboard shows commits completing on schedule. An analyst reports data that is 20 minutes old. What is the most likely cause, and what does it say about the promise?**
   A. Query caching is serving stale results, so the fix is cache invalidation on commit
   B. The write buffer is not on the read path: rows are committed on schedule but only become visible to readers when a conversion step runs, so the true p99 is interval + commit + conversion lag. The dashboard is green because it measures commits rather than visibility, and the promise was made on a metric upstream of the one the analyst experiences
   C. The promise quoted the mean rather than the p99, which is interval ÷ 2 + commit, so the real figure was always about double
   D. Compaction is behind, so recently written files have not yet been merged into the table
   Answer: B — Conversion lag is the term that turns a correct interval calculation into a promise that is wrong by an order of magnitude while every ingest metric stays green, and it applies exactly when a query cannot see a buffered row until the converter has run. The mean-versus-p99 error is real and this lesson insists on the p99, but it is a factor of about two rather than four, and it would not produce a 20-minute observation on a 5-minute interval. Compaction backlog raises read amplification and planning cost without delaying visibility — a small file is still a visible file. Caching is worth checking and is a different failure: it would show identical staleness for all consumers rather than a consistent lag behind commit.

**Q3. A product team asks to move from 15-minute to 30-second batches "for the dashboard". The finance-facing question follows: what does that change cost? Which reply survives the room?**
   A. "Freshness is a query-side concern, so there is no ingest cost to quantify."
   B. "About 30× more commits, so we should assume roughly 30× the cost."
   C. "30× the commits at identical data volume, so about 69,000 files a day averaging under 9 MB instead of about 2,300 averaging 260 MB. The ladder back to the target file size costs two compaction passes rather than one — every ingested byte written three times instead of twice, forever — and compaction must sustain the new creation rate with at least 1.2× headroom or the backlog grows without bound. On our pricing shape that lands as rewrite bytes and request count, plus planning cost from the file count. The cheaper point on the curve is five minutes, and the side I would not promise is sub-minute freshness."
   D. "We can absorb it: the additional files are small, and storage is the cheapest line item we have."
   Answer: C — It quantifies both axes as counts the asker can redo, names the standing cost as a bill rather than a ratio — every byte written three times, forever — states the rate condition that has no steady state when it fails, translates into the pricing *shape* rather than a currency figure, and closes with a cheaper counter-offer and an explicitly unpromised side. The second option has the right multiplier attached to the wrong quantity: 30× the commits is not 30× the cost, because the compaction ladder and the planning cost scale differently from the commit count. The last option is the folklore this course is built to remove: the cost of small files is almost never storage, it is rewrite volume, request count and metadata read on every query. And treating freshness as query-side ignores that the interval is the single input that sets file count, file size and compaction rate simultaneously.

**Read the Iceberg spec's *Delete Formats* section end to end**, then its *Scan Planning* rules for when a delete file must be applied to a data file. Those two sections together are the actual cost model for CDC on a table format, and they are more precise than any blog post about it: the scoping rules — same partition, sequence number comparisons, global application for unpartitioned equality deletes — are what decide whether your change stream costs one file or all of them.

**On the connector side**, Debezium's documentation is the reference for what a change event contains and why ordering and per-key latest-value resolution are the consumer's problem rather than the producer's. The architectural point worth extracting: a CDC stream is a *log of operations*, and a columnar table is a *set of rows*, so somewhere in your pipeline there is a reduction from operations to current state. Whether that reduction happens at write time (copy-on-write, expensive writes) or at read time (delete files, expensive reads) is the whole design decision, and it is the same choice C5.L3 priced.

**For the streaming-is-micro-batch claim**, the primary sources are the engines' own writes documentation: Flink's Iceberg sink and Spark Structured Streaming both commit in groups on an interval, because the unit of visibility in a table format is a snapshot. Reading either one for ten minutes permanently changes how you hear the word "streaming" in a requirements meeting.

**For the estimation habit** — the expected-files-touched formula above is the classic occupancy or coupon-collector shape, and it saturates fast. It is worth internalising as an instinct rather than an equation: *once the number of changes is a few multiples of the number of files, every file is affected.* That single fact reframes most CDC-onto-columnar conversations.
