# C3.L2 — What the Footer Cannot Tell You

_Track C3: Table Formats · ~20 min · columnspaces_

> Flip one byte inside a data page and the file still opens, the footer still parses, 131,072 rows still come back, and the aggregate is silently wrong. Three cruder corruptions are refused instantly. That asymmetry is the finding.
C3.L1 handed you an authoritative footer: it tells you what the file contains, where every column lives, and what each chunk's values are bounded by. This lesson is about the three places that authority ends, because a reader that does not know where it ends produces plausible garbage — and plausible garbage in an analytics platform becomes a number in a report that somebody makes a decision on.

The three limits, stated before the evidence:

1. **Statistics are optional, and absent is not zero.** Every field of the `Statistics` struct is optional. A chunk with no min/max pair cannot be pruned on any predicate — not "pruned as if empty", *not prunable*. A recorded null count of zero is a proof; a missing one proves nothing.
2. **Page checksums are optional too, and the asymmetry that creates is severe.** Corruption that damages *structure* is refused loudly. Corruption that damages a *value* is not detected at all, because there is nothing to check the value against.
3. **A reader's only correct response to an inconsistent file is refusal.** Not a best effort, not a partial answer, not a zero. This is the one place in the whole course where the right behaviour is to return less than you were asked for.

The first is a bill. The second and third are correctness, and they are the reason forge lab 04's `rejects_malformed` check exists.

## The centrepiece: four mutations, three refusals, one silence

The parquet-anatomy lab does not describe corruption. It mutates the bytes of a real file that DuckDB wrote, hands each mutated copy back to the engine, and prints the engine's **own** error text — never a string authored by the lesson. Four mutations, ordered by how deep into the format they reach.

| mutation | what it damages | outcome |
|---|---|---|
| truncate the last 8 bytes | the footer length and the trailing magic | **refused** — `Invalid Input Error: No magic bytes found at end of file` |
| overwrite the trailing `PAR1` | the format identifier, every other byte intact | **refused** — four bytes out of the whole file, and the file is gone |
| write an impossible `footer_len` | the 4-byte little-endian length before the magic | **refused** — the magic still says Parquet, then the file claims a footer larger than itself |
| **flip one byte inside a data page** | one value, in one chunk, of one column | **not refused** |

Read the last row twice. The footer parses. The schema is intact. The statistics are intact. The row count comes back **exactly right — 131,072 rows** — and the aggregate over the corrupted column is wrong, with no error, no warning and nothing in any log.

The reason is one word in the specification. `PageHeader` carries `4: optional i32 crc`, and the writer that produced this file does not emit it. There is no checksum to compare the page against, so a bit-rotted value is simply a different value. Note also how the mutation was *aimed*: the lab locates the byte to flip from the footer's own chunk entry for the column it is about to checksum — `data_page_offset + total_compressed_size / 2` of the middle row group — because "a third of the way into the file" is a guess that can land in bytes the query never decodes and prove nothing. That the footer can aim a corruption is C3.L1's first claim, used in anger.

The lab reports this **whichever way it comes out.** If a future build refuses the byte flip, that is an improvement over what the lesson predicts and the result is surfaced as an anomaly rather than swallowed. If the flipped byte happens not to change the answer, the lab says the run did not demonstrate silent corruption instead of claiming a finding it did not get.

> **[vendor snapshot — verified 2026-09]** Optionality in the Parquet specification: statistics, checksums, and what a reader may assume
>
> Straight from the Thrift definition and the format README:
> 
> - **`PageHeader` field 4 is `optional i32 crc`.** The README's "Checksumming" section explains the intent: *"Pages of all kinds can be individually checksummed. This allows disabling of checksums at the HDFS file level, to better support single row lookups."* The CRC is computed with standard CRC32 over the serialised page body **excluding the page header**, after compression and encryption. Optional means a conforming writer may omit it and a conforming reader has nothing to verify.
> - **Every field of `Statistics` is optional** — `min_value`, `max_value`, `null_count`, `distinct_count`, `nan_count` — and the bound fields are documented as *bounds*, with `is_min_value_exact` / `is_max_value_exact` flags precisely because writers may store shorter, looser values. On `null_count` the spec is explicit that readers must distinguish "not present" from "== 0" and **must not assume zero when it is absent.**
> - The **"Error recovery"** section states the blast radius per level: corrupt file metadata loses the file; a corrupt column chunk loses that chunk (other row groups of the same column survive); a corrupt page header loses the remaining pages in that chunk; corrupt data within a page loses that page. It adds the honest note that the file is more resilient with smaller row groups.
> 
> **What was observed here rather than documented:** on the DuckDB builds this course's lab runs against, the Parquet writer does not emit page CRCs, so the value-corruption probe is not refused — the footer parses and the query returns a wrong answer. That is a measurement from the lab in your tab, not a vendor commitment, and the lab is written to report the opposite result if a future build changes it. Check your own writer before relying on either behaviour, and treat storage-layer integrity (object-store checksums, end-to-end hashes on ingest) as the control that actually covers this, because the format does not by default.
>
> Sources: https://raw.githubusercontent.com/apache/parquet-format/master/src/main/thrift/parquet.thrift · https://github.com/apache/parquet-format/blob/master/README.md

## None is not zero, and the branch that gets it wrong drops rows

C2.L1 established this at the planner level. Here is the same rule stated as a reader's obligation, because forge lab 04 grades it in a format where you can see the byte that decides it.

The lab reads **KSPQ** — a Parquet-*shaped* teaching format the harness generates, not real Parquet. In its footer, each column chunk entry carries a single `u8 has_stats` flag:

```text
u64  chunk_offset
u64  chunk_len
u8   has_stats            0 or 1
if has_stats == 1:
  i64  min                over non-null values
  i64  max
  u32  null_count
```

`has_stats == 0` means **the writer recorded nothing**. It does not mean min 0, max 0, null count 0. One byte separates "I promise nothing lies outside this range" from "I make no promise", and a reader that collapses them has two failure modes with very different severities:

- Treating **absent as zero** turns `IS NULL` into a skip for every chunk whose writer simply did not record the count. Silently wrong answer, no error anywhere. This is the incident.
- Treating **a recorded zero as absent** means reading chunks you could have proven irrelevant. Inflated bill, correct answer. This is the annoyance.

They are not symmetrical, and the asymmetry is the rule: **when metadata is missing, read the data.** Being unable to prune costs money; being wrong about a bound costs credibility. The same ordering appears in the harness's own message for the statistics check in lab 02 — *"None means the writer recorded nothing, which forbids the planner from ever pruning this column."*

## What forge lab 04 makes you prove — and exactly what it is

Lab 04 (`parquet-reader`, "Read the Real Thing") is where reading someone else's bytes stops being a description. You implement `read_footer`, `parse_footer`, `read_chunk` and `project` against a `Source` trait that only exposes a length and a `read(offset, len)` — there is no `&[u8]` of the whole file, because that is not what object storage gives you and because a reader handed the whole file cannot be measured.

**Be precise about the format, because the lab is.** KSPQ has the four things that make a Parquet-shaped file readable — a leading magic (`KSPQ`), a footer at the END, per-column-chunk offsets and lengths, and per-chunk statistics — and deliberately omits everything that makes real Parquet a week of plumbing:

- **no Thrift.** Every integer is fixed-width little-endian, so there is no compact-protocol decoder to write.
- **no pages.** A KSPQ chunk is one flat payload: no page headers, no dictionary page, no per-page statistics, and **no CRCs** — which is why the byte-flip finding above comes from the DuckDB lab and not from this one.
- **no definition or repetition levels.** Nulls are a flat bitmap; there is no nesting at all.
- **no encodings and no compression codecs.** Values are stored plain — you already wrote the codecs in lab 01.
- **one physical type** (`i64`) with three logical annotations, and a flat column list rather than a schema tree.
- **no `ColumnIndex`/`OffsetIndex` and no bloom filters**, so pruning stops at the row group.
- **no trailing magic.** Real Parquet's last eight bytes are `[footer_len : u32 LE][PAR1]`; KSPQ's last four are just the length, so the offset arithmetic lives in one place.

What transfers completely is the *job*: seek to the end to find out what the file contains, fetch only the ranges the query needs, and refuse a file that does not describe itself consistently.

Two of the five checks are this lesson's:

**`projection_reads_minimum` is graded as a count, and the threshold is zero.** The harness wraps the file in a `Source` that records every `(offset, len)` you request, then asserts that a two-column projection touched **zero bytes** of the other columns' chunks. Not fewer bytes. Zero. Reading a whole row group into memory and slicing it is simpler to write and passes every other check in the suite — and it is exactly the bug that makes a columnar reader cost the same as a row-store scan, invisibly. Note the honest simplification: a production reader usually fetches a speculative 8–64 KiB tail in one request to save a round trip, and if you fetch a tail large enough to cover a chunk, the harness will correctly call those bytes work you did not need.

**`rejects_malformed` is a list of refusals, and never a panic.** A file shorter than 8 bytes, wrong leading magic, a `footer_len` longer than the file, a footer that ends mid-structure, an unknown version or type tag, a chunk range outside the file, a chunk payload that contradicts its own declared length, a projection naming a column that does not exist. Each is an `Err`, each carries the numbers that make it diagnosable — and a panic traps the wasm module, so the browser says "not implemented yet" and the reader learns nothing. The template gives you a bounds-checked `Cursor` whose every method returns `Result` for exactly this reason: if you find yourself writing `bytes[i]`, you have written the panic the check is looking for.

The subtle one is the `footer_len` bound check. A `footer_len` larger than the file is what a truncated upload looks like, and `file_len − 4 − footer_len` **underflows into an enormous offset**. A reader that lets that through either errors far away from the cause or reads memory that is not its own.

_fig 1 — four mutations to one real file, and the only one the format cannot catch_

Components: one real Parquet file · 131,072 rows · written by DuckDB (each probe runs against a mutated COPY; the original stays readable afterwards) · truncate 8 bytes (length + trailing magic) · clobber PAR1 (4 bytes of identity) · lie about footer_len (points outside the file) · flip 1 data byte (aimed from the footer) · refused — with the engine's own message ("Invalid Input Error: No magic bytes found at end of file") · accepted (no error at all) · structural damage is LOUD (the query fails; nobody makes a decision on it) · 131,072 rows, wrong sum (value damage is SILENT; the report looks fine) · because PageHeader field 4 is `optional i32 crc`, and this writer omits it (there is nothing to check the value against — so integrity has to come from the storage layer, not the reader)

Steps:
1. Start from a file the engine wrote itself and can read correctly, then mutate copies of its bytes. Nothing here is simulated: the engine is asked to read each damaged copy and its own error text is what gets printed.
2. Three mutations damage structure the footer needs in order to be parsed at all — the length field, the identity magic, and a length that points outside the file. All three reach into the last eight bytes or what they describe.
3. All three are refused before a value is decoded, and the refusal is the good outcome: the query fails, somebody gets paged, and no number reaches a dashboard. This is the behaviour forge lab 04 grades as rejects_malformed.
4. The fourth mutation flips a single byte inside a data page, aimed using the footer's own chunk entry so it lands in bytes the checked query actually decodes rather than somewhere harmless.
5. It is not refused. The footer parses, the schema is intact, the statistics are intact, all 131,072 rows come back, and the aggregate is wrong — with no error and nothing in any log to notice.
6. The cause is one word in the specification: the page checksum is optional, and this writer omits it. Nothing exists to compare the page against, so integrity has to be someone else's job — the storage layer's, or your ingest pipeline's.

---

- **1 byte** — enough to make a query silently wrong (Flipped inside a data page, located from the footer. The row count is unchanged and the aggregate no longer matches the original.)
- **3 of 4** — corruptions the engine refuses (Truncated tail, clobbered magic and an impossible footer length are all structural. The fourth is a value, and the format does not protect values by default.)
- **0 bytes** — the threshold for projection_reads_minimum in forge lab 04 (The harness records every byte range you request and fails the check if a single byte of an unprojected chunk was fetched. A count, not a duration.)
- **0 ≠ absent** — a recorded null count of zero versus no entry at all (Zero is a proof that IS NULL cannot match. Absent proves nothing and forces a read. The specification tells readers not to assume zero when the field is missing.)

> **[segfault]** Both of these compile, pass casual testing, and are wrong in ways no error message will ever point at.
> 
> ```rust
> // 1. trusting a length you have not bounded.
> let footer_start = file_len - 4 - footer_len as u64;   // underflows on a truncated upload
> ```
> 
> On a file whose `footer_len` is larger than the file — which is what a killed upload looks like — this wraps to an enormous offset. Best case you get an out-of-bounds error a long way from the cause. Worst case, in a language without the bounds check, you read whatever is next in memory and parse it as a schema. `rejects_malformed` exists for this line.
> 
> ```rust
> // 2. deciding nullity from the value instead of the bitmap.
> let v = cursor.i64()?;
> values.push(if v == 0 { None } else { Some(v) });      // every legitimate 0 is now NULL
> ```
> 
> A null row stores eight zero bytes and so does a genuine zero. The bitmap is the only thing that distinguishes them, which is precisely why it exists — and this bug quietly deletes every zero in the table while returning the right row count.
> 
> The pattern in both: **a reader that guesses produces plausible output.** Plausible output is worse than a crash, because a crash gets fixed on Tuesday and a plausible number gets presented on Thursday.

---

> **[info]** If the format does not protect values by default, something else has to. Four controls, in rough order of how much they cover per unit of effort:
> 
> - **The object store's own checksums.** Every major object store verifies content on read against a checksum stored with the object, and will let you supply one on write. This is the control that actually covers bit rot in storage, and it is usually already on.
> - **An end-to-end hash recorded at ingest**, compared when a file is registered into the table. This is the one that catches a truncated or mangled *transfer*, which is the failure mode that produced C3.L1's unreadable file.
> - **Enabling page CRCs in your writer if it offers them.** Cheap, and it converts a silent wrong answer into a loud refusal. Check whether yours does; do not assume.
> - **A cheap reconciliation query on a schedule** — row counts and a sum per partition against the source of truth. Crude, but it is the only one of the four that catches a *logical* error in the pipeline, which is a much more common cause of wrong numbers than bit rot has ever been.
> 
> None of these is the reader's job, and that is the point. **A reader's contract is to refuse what it cannot parse and to be exactly right about what it can.** It cannot promise the bytes were the bytes you wrote.

---

_refuse-or-be-exact ≡ three contracts you already hold_

- **a JSON parser** (A malformed document is an error, not a partial object. Nobody expects a parser to guess at a missing brace, because the guess would be indistinguishable from real data downstream.) ≡ **a Parquet reader** (Same contract at a much higher stake: the output is aggregated, charted and decided upon, so a guess propagates further before anyone can question it.)
- **TCP checksums versus application-level correctness** (The transport proves the bytes arrived as sent. It says nothing about whether they meant what you thought — that is the application's problem, and it needs its own check.) ≡ **page CRCs versus pipeline reconciliation** (A CRC would catch a flipped bit. It would not catch a loader that wrote the wrong column. Both need an owner, and they are not the same owner.)
- **a NULL column in SQL versus a missing column** (One is a value that says "unknown", the other is a schema fact. Collapsing them is how a query returns rows nobody asked for.) ≡ **null_count == 0 versus no statistics entry** (One is a proof and the other is an absence of proof. Collapse them in the skip direction and you drop every null row in the table with no error anywhere.)

**Q1. A finance dashboard has been reporting a revenue total that is 0.3% low for three weeks. The Parquet files parse cleanly, row counts match the source system exactly, and no query has ever errored. Which hypothesis does this lesson tell you to take seriously, and what do you do about it?**
   A. Statistics are stale, so the planner is skipping row groups that hold matching rows; recollect statistics and the total will correct itself
   B. Value-level corruption is not detected by default — page CRCs are optional and many writers omit them, so a damaged page returns the right row count and a wrong aggregate. Reconcile a checksum per partition against the source, and put integrity controls at the storage and ingest layers rather than expecting the reader to catch it
   C. The row count matching proves the data is intact, so the bug must be in the dashboard's aggregation logic and the storage layer can be ruled out
   D. A truncated file is being skipped silently by the reader, so the fix is to fail queries when any file in the table is unreadable
   Answer: B — The symptom is diagnostic: correct row count, no error, wrong aggregate. That is exactly the signature the anatomy lab produces by flipping one byte inside a data page — the footer parses, all 131,072 rows return, and the sum no longer matches, because there is no page checksum to compare against. Stale statistics would cause a *low row count* by skipping blocks (and pruning that drops matching rows is a false negative, which forge lab 02 grades pass/fail), so the matching count argues against it rather than for it. A matching row count does not prove intactness at all — that is the whole asymmetry. And a truncated file is refused loudly rather than skipped, so it cannot be silent. The controls that cover this live in storage checksums, ingest hashes and reconciliation, not in the reader. Dashboard logic is worth checking too, but it does not explain why the total drifted three weeks ago and stayed there.

**Q2. A reader parses a footer whose declared footer_len is larger than the whole file. What must it do, and why is this case singled out?**
   A. Clamp footer_len to the file size and parse as much of the footer as fits, so partially uploaded files remain queryable
   B. Return an error naming the declared length and the file length, without computing footer_start at all — because file_len − 8 − footer_len underflows into an enormous offset, and a truncated upload is precisely what produces this input
   C. Assume the file was written by a newer version and skip to reading the data region directly
   D. Return zero rows, since the file is empty as far as this reader can determine
   Answer: B — This is the check people skip, and it is the interesting failure. The trailing magic can still be intact while the length field is nonsense, so the file passes the identity check and then claims a footer bigger than itself. Subtracting an unbounded length from the file length underflows, and the resulting offset either errors far from the cause or reads memory the process does not own. Clamping is worse than erroring: the footer is a Thrift structure, so a prefix of it is not a valid smaller footer — you would be parsing arbitrary bytes as a schema. Returning zero rows is the most dangerous option on the list, because it converts a broken file into an empty one, and an empty answer aggregates into a report without complaint. forge lab 04 lists this as BadFooterLen with both numbers carried in the error, because "invalid file" is not a bug report.

**Q3. A colleague's reader passes footer_parse, rowgroup_metadata and storm, but fails projection_reads_minimum on forge lab 04. Their implementation reads each row group's full byte range once and slices the requested columns out of memory. What is your reading of the failure?**
   A. The check is too strict — the reader returns correct values, and slicing in memory is a legitimate optimisation that avoids extra requests
   B. The check is measuring the thing the format exists for: the harness records every requested byte range and requires that a two-column projection touch zero bytes of the other chunks. Reading whole row groups makes a columnar reader cost what a row-store scan costs, and no test of correctness would ever notice
   C. They should reduce the row-group size so that reading a whole row group fetches fewer bytes
   D. The failure is caused by not fetching a speculative tail, which the harness expects readers to use
   Answer: B — Correct values are necessary and nowhere near sufficient: every other check in the suite passes for this implementation, which is exactly why the instrumentation is the lab. Column chunks are contiguous precisely so a projection is a set of ranges, and a reader that materialises whole row groups has discarded the single property that makes columnar storage cheaper than a row store — while remaining perfectly correct and therefore silent about it. Shrinking row groups reduces the waste per request without removing the bug, and it buys the footer growth C3.L1 measured. The speculative tail runs the other way: fetching a large tail can pull in chunk bytes you did not need, and the harness will count those against you, which is why the lab notes the simplification instead of hiding it.

**Read the `optional` keywords in `parquet.thrift` as a design document.** Every one of them is a place where two conforming implementations can legally disagree about what a file tells you: statistics, per-page indexes, bloom filters, the page CRC, `distinct_count`, sort orders. A reader is a set of decisions about what to do when each is absent, and the honest ones are documented rather than implied.

On silent data corruption, the empirical literature is worth a look because it calibrates how much of your worry belongs to storage and how much to your own pipeline. **Bairavasundaram et al., "An Analysis of Latent Sector Errors in Disk Drives" (SIGMETRICS 2007)** and the companion **"An Analysis of Data Corruption in the Storage Stack" (FAST 2008)** measured checksum mismatches across a very large deployed fleet; **Schroeder, Lagisetty and Merchant, "Flash Reliability in Production" (FAST 2016)** did the equivalent for SSDs. **ZFS's end-to-end checksums** are the standard architectural answer, and reading why ZFS refused to trust the layer below it is the fastest way to internalise where a checksum has to live to be meaningful. The uncomfortable takeaway for an analytics platform: modern object storage handles the bit-rot case well, which means most of your wrong numbers will come from your own transformations — and those are caught by reconciliation, not by CRCs.

For refusal as a design stance, the parsing community has the sharpest writing: **"Parse, don't validate"** on making illegal states unrepresentable, and the LangSec work on **the recogniser/parser distinction** (Bratus, Patterson, Sassaman et al.) which argues that most exploitable bugs are parsers that accepted input a stricter grammar would have rejected. `rejects_malformed` is that argument, graded.

For the specific problem of a reader that must not trust its input while still being fast, **arrow-rs**'s `ParquetMetaDataReader` is a good study: how it bounds the footer length against the file size before allocating, how it handles the speculative tail, and where it chooses to return an error rather than a partial `FileMetaData`.

Next: **C3.L3**. One file that refuses to be read is a manageable incident. The real question is how a *table* made of thousands of these files decides which of them are currently part of it — and what atomicity rests on when the storage underneath offers you almost nothing.
